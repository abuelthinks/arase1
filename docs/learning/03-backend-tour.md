# Lesson 03 — The Backend Tour

**Goal:** Follow a request through Django from the moment it arrives to the JSON that goes back.
After this you can answer: *"the frontend called `/api/students/5/profile/` — what code runs,
and where does the data come from?"*

We'll use two real endpoints: the **student profile** (`StudentProfileView`) and the
**student list/create** (`StudentViewSet`). Open [`api/views.py`](../../api/views.py),
[`api/urls.py`](../../api/urls.py), [`api/models.py`](../../api/models.py), and
[`api/serializers.py`](../../api/serializers.py).

---

## 1. The backend's job, in one sentence

> Receive an HTTP request → figure out who's asking → check they're allowed → read or write the
> database → send back JSON.

Everything below is just *where* each of those steps lives.

---

## 2. The request lifecycle (the order things run)

When `http://localhost:8000/api/students/5/profile/` arrives, Django runs this pipeline:

```
1. backend/urls.py        "Which app handles /api/...?"  → hands off to api/urls.py
2. api/urls.py            "Which view handles students/5/profile/?" → StudentProfileView
3. middleware + auth      "Who is this?" reads the cookie → sets request.user
                          (api/authentication.py + Django middleware)
4. permission check       "Is request.user allowed?"  (permission_classes on the view)
5. the view method        get()/post()/... runs your logic
       │
       ├─► api/services/*  the actual business logic (the heavy lifting)
       │        │
       │        └─► models (api/models.py)  ──► the database (db.sqlite3)
       │
       └─► serializer (api/serializers.py)  turns DB objects into JSON
6. Response               JSON travels back to the browser
```

Keep this list visible. When debugging the backend, you'll ask "which of these six steps went
wrong?" — and each step is a specific file.

---

## 3. Step 1–2: URLs — the switchboard

A URL is just an address; the **URL config** says which code answers each address.

### Top level: `backend/urls.py`
Open it. The key line is:
```python
path('api/', include('api.urls')),
```
Translation: *"anything starting with `/api/`, go ask `api/urls.py`."* You'll also see the
auth endpoints here (`/api/auth/token/`, `/api/auth/me/`, …) pointing at `auth_views.py`.

### App level: `api/urls.py`
This file maps the rest of the path to a **view** (the code that handles it). There are **two
styles** in here, and recognizing them saves you a lot of confusion:

**Style A — explicit `path(...)` for one-off endpoints:**
```python
path('students/<int:student_id>/profile/', StudentProfileView.as_view(), name='student-profile'),
```
Read it as: URL `students/<a number>/profile/` → run `StudentProfileView`, and capture the
number as `student_id`. That `student_id` is handed straight to the view method. This is the
profile endpoint our frontend page called last lesson.

**Style B — a `router` for "resource" endpoints (ViewSets):**
At the top of `api/urls.py`:
```python
router = DefaultRouter()
router.register(r'students', StudentViewSet, basename='student')
```
A router is a shortcut. This **one line** auto-creates a whole family of URLs for students:

| Method + URL | What it does | ViewSet method |
|---|---|---|
| `GET /api/students/` | list all students | `get_queryset` / `list` |
| `POST /api/students/` | create a student | `create` |
| `GET /api/students/5/` | get one student | `retrieve` |
| `PATCH /api/students/5/` | edit a student | `partial_update` |
| `DELETE /api/students/5/` | delete a student | `destroy` |

> **Debugging payoff:** If a frontend call is `api.get('/api/students/')`, don't search for a
> URL literally named that — it's generated by `router.register('students', StudentViewSet)`.
> Go straight to `StudentViewSet` in `views.py`. If it's a specific path like
> `/api/students/5/profile/`, search `api/urls.py` for `profile`.

## 4. Step 5: Views — the request handlers

A "view" is the function/class that runs for a URL. ARASE uses two shapes:

### Shape A — `APIView` (one endpoint, you write the methods)
`StudentProfileView` is the whole pattern in 10 lines. Read it (around line 1323 of `views.py`):

```python
class StudentProfileView(APIView):
    permission_classes = [permissions.IsAuthenticated]   # (a) must be logged in

    def get(self, request, student_id):                  # (b) handles GET; gets student_id from the URL
        try:
            if request.user.role == 'ADMIN':              # (c) admins see any student
                student = Student.objects.get(id=student_id)
            else:                                          #     others only their assigned students
                student = Student.objects.get(id=student_id, assigned_users__user=request.user)
        except Student.DoesNotExist:
            return Response({"error": "Student not found or access denied."}, status=404)  # (d)

        from .services.student_service import get_student_profile_data
        return Response(get_student_profile_data(student, request.user))   # (e) hand off to a service
```

Walk the labels — this is *the* template for reading any view:
- **(a) `permission_classes`** — the gate. `IsAuthenticated` = "must be logged in or get 401."
- **(b) `def get(self, request, student_id)`** — the method name matches the HTTP verb. `GET`
  runs `get`, `POST` runs `post`. `student_id` arrived from the URL pattern.
- **(c) the role check** — security lives here, not in the frontend. Note how non-admins are
  restricted by `assigned_users__user=request.user` (we'll decode that query in §5).
- **(d) error response** — couldn't find/allowed → return 404 with a message. *This is the exact
  text the frontend's `error` state would show.*
- **(e) the hand-off** — the view doesn't compute the profile itself; it calls
  `get_student_profile_data(...)` in `api/services/student_service.py`. **That's where the real
  logic is.** Views stay thin on purpose.

### Shape B — `ViewSet` (a whole resource at once)
`StudentViewSet` (top of `views.py`, ~line 51) handles list/create/update/delete for students
together. You don't write `get`/`post`; you override named methods:

```python
class StudentViewSet(viewsets.ModelViewSet):
    serializer_class = StudentSerializer            # which translator to use
    permission_classes = [permissions.IsAuthenticated]

    def get_queryset(self):                         # which rows this user is allowed to see
        user = self.request.user
        if user.role == 'ADMIN':
            qs = Student.objects.all()              # admins: everyone
        else:
            qs = Student.objects.filter(assigned_users__user=user).distinct()  # others: only assigned
        return qs.order_by(...)                     # (sorted by urgency — read the comments)

    def create(self, request, *args, **kwargs):     # runs on POST /api/students/
        if request.user.role != 'ADMIN':
            return Response({"error": "Only admins can register students."}, status=403)
        ...
        student, invitation = create_student_with_invitation(...)   # again: service does the work
        return Response(StudentSerializer(student).data, status=201)
```

Same lessons: a gate (`permission_classes` + role checks), and the heavy lifting pushed into a
service (`create_student_with_invitation`). `get_queryset` is the single most important method
on a ViewSet — **it decides which database rows the user is even allowed to see.** Most
"why can't this user see that student?" bugs are answered right here.

## 5. Step 5 (cont.): Models — the shape of the data

Open [`api/models.py`](../../api/models.py). Each `class` is one **table** in the database, and
each attribute is a **column**. The `Student` model is refreshingly small:

```python
class Student(models.Model):
    STATUS_CHOICES = ( ('PENDING_ASSESSMENT','Pending Assessment'), ... ('ARCHIVED','Archived') )
    first_name = models.CharField(max_length=100)
    last_name  = models.CharField(max_length=100)
    date_of_birth = models.DateField()
    grade  = models.CharField(max_length=50)
    status = models.CharField(max_length=30, choices=STATUS_CHOICES, default='PENDING_ASSESSMENT')
```

Reading a model tells you exactly what data exists. `Student` has a name, DOB, grade, and a
`status` that's one of six fixed values. That `status` field drives a lot of the app — the
comment above it even draws the lifecycle:
`PENDING_ASSESSMENT → ASSESSMENT_SCHEDULED → ASSESSED → ENROLLED ↔ INTEGRATED → ARCHIVED`.

### Relationships: `ForeignKey` and `related_name`
Models link to each other. Look at `StudentAccess` (the table that says "this user is assigned
to this student"):

```python
class StudentAccess(models.Model):
    user    = models.ForeignKey(User,    related_name='student_access',  on_delete=models.CASCADE)
    student = models.ForeignKey(Student, related_name='assigned_users',  on_delete=models.CASCADE)
```

- A `ForeignKey` means "points at one row in another table." So each `StudentAccess` row links
  one `User` to one `Student`.
- `related_name='assigned_users'` is the **reverse** name. It lets you go *from a student* to
  *its access rows* by writing `student.assigned_users`. **This is the secret decoder for that
  query in the view:** `Student.objects.filter(assigned_users__user=request.user)` means
  *"students that have an access row whose user is me."* That's the entire permission model for
  non-admins, and now you can read it.

### Querying: the `.objects` API
The way Python talks to the database. You don't write SQL; you chain methods:

| Code | Meaning |
|---|---|
| `Student.objects.all()` | every student |
| `Student.objects.get(id=5)` | the one student with id 5 (errors if 0 or 2+) |
| `Student.objects.filter(status='ENROLLED')` | all enrolled students (0 or more) |
| `Student.objects.filter(...).exists()` | True/False — does any match? |
| `qs.order_by('-id')` | sort, newest first (the `-` means descending) |

You've already seen all of these in the views above. When you spot `SomeModel.objects.<something>`,
that line is **reading or writing the database** — flag it mentally, because data bugs live there.

## 6. Step 5 (cont.): Serializers — DB objects ⇄ JSON

A Django model object isn't JSON; the browser needs JSON. **Serializers translate between the
two.** Open [`api/serializers.py`](../../api/serializers.py) and find `StudentSerializer`:

```python
class StudentSerializer(serializers.ModelSerializer):
    has_parent_assessment = serializers.SerializerMethodField()   # a COMPUTED field
    ...
    class Meta:
        model = Student
        fields = ['id', 'first_name', 'last_name', 'date_of_birth', 'grade', 'status',
                  'has_parent_assessment', ...]

    def get_has_parent_assessment(self, obj):
        return ParentAssessment.objects.filter(student=obj).exists()
```

Three things to take away:
- **`fields = [...]`** is the contract: *exactly these keys* appear in the JSON the frontend
  receives. If the frontend says `data.student.grade` is `undefined`, check that `grade` is in
  this list. The frontend can only see what the serializer exposes.
- **`SerializerMethodField`** = a field that isn't stored in the database but **computed on the
  fly**. `has_parent_assessment` isn't a column on `Student`; the matching `get_has_parent_assessment`
  method runs a query to figure it out. So if a computed value looks wrong, find its `get_...`
  method here — that's the logic.
- **`ModelSerializer`** is the shortcut version that reads the field types from the model for you.

## 7. Step 3: How the server knows who you are

You never send a password on each request — yet `request.user` is always set. How?

When you logged in, the server put your identity into a **JWT** (a signed token) inside an
**HttpOnly cookie** (a cookie JavaScript can't read, so it can't be stolen by scripts). The
browser sends that cookie automatically on every request (remember `withCredentials: true` from
`api.ts`). On the server, [`api/authentication.py`](../../api/authentication.py) reads the cookie,
verifies the token, and sets `request.user`. That's why every view can just say `request.user`.

You rarely edit this — but knowing it exists explains a whole class of bugs: "I'm logged in but
the server says 401" almost always means the cookie didn't arrive or the token expired. (Lesson
06 has the checklist.)

## 8. The `services/` layer — where logic actually lives

Open the [`api/services/`](../../api/services/) folder. There's one file per topic:
`student_service.py`, `iep_service.py`, `notification_service.py`, `report_service.py`, and so on.

The pattern, one more time: **views decide *if* something should happen and who's allowed;
services decide *how* it happens.** When you want to understand *what a feature does*, the view
just points the way — open the service it calls. `StudentProfileView` calls
`get_student_profile_data` in `student_service.py`; that function is where the profile JSON is
actually assembled.

This is genuinely good structure (not all vibe-coded apps have it). Lean on it: the file names
in `services/` are basically a table of contents for your app's capabilities.
