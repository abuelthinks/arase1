Reading & Understanding the ARASE Codebase

A self-paced course for the ARASE team. You built this app fast, often with AI help. This course teaches you to read it, understand it, and fix it yourself, so when something breaks and there's no AI around, you know where to look.

It's written for people who can write code with help but get lost reading it. No CS background needed. Every example comes from this codebase, with real file paths.

Last checked against the code: October 2026 (commit de268bf). If a line number is a little off, search for the function name instead. Names move less than line numbers.

The one idea everything hangs on

Almost everything in this app is a round trip: the browser asks the server a question, the server answers, the screen updates.

  YOU click something
        │
        ▼
  BROWSER (Next.js / React)  ──── HTTP request ────►  SERVER (Django, run by daphne)
   frontend/src/...                                    api/ + backend/
        ▲                                                   │
        │                                                   ▼
        └──────────── JSON response ◄──────────────  DATABASE (SQLite in dev, Postgres live)

If you can follow one round trip all the way through (which files run, in what order), you can debug almost anything here. Lesson 04 walks two of them. Lesson 05 covers the cases that aren't a simple round trip: slow AI jobs that run in the background, and live updates pushed to the screen.

How to study this together

  1. Point, don't just read. When a file is named, open it and put your cursor on the line. Reading about code without looking at it doesn't stick.
  2. Guess before you look. Many lessons have a Predict box. Write your guess down first, then check. Being wrong and then seeing why is how this sticks.
  3. Do the exercises. Each lesson ends with 2–4 short tasks. Answers are at the very bottom of each lesson, so you can check yourself without peeking by accident.
  4. You don't need to understand every line. The goal is knowing how to find the part you need. Nobody holds 3,000 lines in their head.
  5. Teach it back. After a lesson, one person explains the trace out loud to the other two. If you can explain it, you understand it.

There's also an interactive version inside the app at /learn (admin accounts) with a clickable map, animated request traces, a symptom finder, and a quiz.

Before you start: get the app running

You can't debug what you can't run. Each of you should be able to start ARASE on your own machine. The full setup is in the root README.md ("Local Development"). Here's what's actually running when you develop:

Terminal Command What it is Restart it when…
1 venv\Scripts\python.exe -m daphne -b 127.0.0.1 -p 8000 backend.asgi:application The Django backend at http://localhost:8000 You change any .py file. daphne doesn't reload by itself.
2 cd frontend then npm run dev The Next.js frontend at http://localhost:3000 Almost never. It reloads on save.
3 venv\Scripts\python.exe -m celery -A backend worker -l INFO --pool=solo The background worker (AI generation, translation) You change api/tasks.py or anything in api/services/.
4 redis-server The message queue Celery needs It crashes or you reboot.

The #1 local gotcha: you fix a bug in Python, refresh the browser, and it's still broken. Nine times out of ten the code is fine and daphne or Celery is still running the old version. Restart them. (python manage.py runserver --settings=backend.settings.dev also works and does reload on save, because daphne is in INSTALLED_APPS. Running daphne directly is just what the team usually does. Know which one you started.)

When it's all running, open http://localhost:3000, log in with a dev account (ask a teammate if you don't have one), and click around. Keep that tab open. You'll be inspecting it constantly.

What "good at reading code" actually means

It is not understanding every line at a glance. Even whoever wrote it can't do that. It means:

  • Knowing where a behavior probably lives, so you can jump straight there.
  • Being able to follow a thread from a button click to the database and back.
  • Turning an error message into "go look at this file."
  • Knowing which tool (browser Network tab, daphne terminal, Celery terminal) answers which question.

That's a skill you can learn, not a talent. Let's go → 01-the-big-picture.md

Lesson 01: The Big Picture

You'll be able to: say in plain words what ARASE is, name the programs that make it up, and know which folder to open for any kind of problem. This is the map for the rest of the course.

Time: ~30 min · Open: the project root in your editor

1. What ARASE is

ARASE manages SPED (Special Education) students: from the first assessment, through enrollment, through monthly progress tracking. AI (Google Gemini) helps write the IEP (Individualized Education Program) and the monthly reports.

Four kinds of people use it. In the code these are called roles:

Role What they do Where they land after login
ADMIN Registers students, builds each student's team, generates IEPs and reports /dashboard
TEACHER Fills in classroom assessments and progress trackers /workspace
SPECIALIST Does professional assessments (speech, OT, …) /workspace (or /specialist-onboarding if their profile isn't finished)
PARENT Fills in parent forms about their child, picks specialists, books appointments /dashboard

You'll see these four words everywhere: user.role === "ADMIN" in TypeScript, request.user.role == 'ADMIN' in Python. A huge part of the app is just "allow or show this depending on who's logged in."

A student's life in the app

Every student has a status, and most screens behave differently depending on it. It's defined on the Student model in api/models.py:

PENDING_ASSESSMENT → ASSESSMENT_SCHEDULED → ASSESSED → ENROLLED ↔ INTEGRATED → ARCHIVED

Roughly: the admin registers a student and invites a parent → parent fills in forms and picks specialists → specialists assess → admin enrolls the student → monthly report cycles start, where everyone fills in trackers → AI turns those into an IEP and monthly reports.

Predict: A teacher says "I can't see the student I was told to work with." Before reading further, guess: is that more likely a problem with the screen, or with who's allowed to see what? (Answer in §3.)

2. The five programs that make up ARASE

ARASE isn't one program. In development, four or five separate programs run at the same time and talk to each other. Knowing this explains a lot of "it works on my machine" weirdness.

  ┌────────────────────┐   HTTP (JSON)    ┌──────────────────────────┐
  │  1. FRONTEND        │ ───────────────► │  2. BACKEND               │
  │  Next.js            │ ◄─────────────── │  Django, served by daphne │
  │  localhost:3000     │                  │  localhost:8000           │
  │  frontend/          │ ◄── WebSocket ── │  api/ + backend/          │
  └────────────────────┘   (live pushes)  └─────────────┬────────────┘
                                                        │ reads/writes      queues slow jobs
                                                        ▼                         │
                                           ┌──────────────────────┐              ▼
                                           │  5. DATABASE          │   ┌──────────────────┐
                                           │  db.sqlite3 (dev)     │   │  4. REDIS         │
                                           │  PostgreSQL (live)    │   │  the job queue    │
                                           └──────────▲───────────┘   └────────┬─────────┘
                                                      │                         │ picks up jobs
                                                      │ writes results          ▼
                                                      │              ┌──────────────────────┐
                                                      └───────────── │  3. CELERY WORKER     │
                                                                     │  api/tasks.py         │
                                                                     │  calls Gemini / Ollama│
                                                                     └──────────────────────┘
# Program Lives in Its job
1 Frontend (Next.js + React + TypeScript) frontend/ Draws the screen, reacts to clicks, asks the backend for data. It never touches the database.
2 Backend (Django + Django REST Framework) api/, backend/ Checks who you are and what you're allowed to do, reads/writes the database, sends back JSON.
3 Celery worker api/tasks.py Runs slow jobs in the background, mainly AI generation and translation, so the backend can answer the browser right away.
4 Redis (installed separately) A fast message queue. The backend drops a job in, Celery picks it up.
5 Database db.sqlite3 in dev Where all the data actually lives. One file locally, PostgreSQL in production.

Plus one outside service: the AI model. AI_PROVIDER in .env chooses it. auto tries Gemini first and falls back to a local Ollama model.

Why split it up? Two reasons that matter for debugging:

  1. Security. You can't trust the browser, since a user can change anything in it. So the rules (who can see which student, who can delete) live on the backend. That's why you'll see permission checks in Python even when the frontend already hides the button.
  2. It tells you where bugs live. Your first question when something breaks is always "which program?" Lesson 07 shows how to answer that in 30 seconds.

4. The two-axis mental model

To understand or fix any feature, place it on two axes:

  1. Which program? Frontend, backend, Celery worker, or database?
  2. Which layer inside it?
    • Frontend: page (app/.../page.tsx) → components → lib/api.ts → network
    • Backend: URL (urls.py) → view (views.py) → service (services/) → model (models.py) → database
    • Background: task (tasks.py) → service → AI → database → live event back to the browser

Every feature sits somewhere on that grid. The rest of the course teaches you to walk it.

Exercises

  1. Roles in the wild. Open api/views.py and search (Ctrl+F) for role != 'ADMIN'. Skim the matches. How common are "admins only" checks? (No exact count needed.)
  2. URL → file. A user visits http://localhost:3000/workspace. Which file draws it? What about http://localhost:3000/students/12/reports?
  3. Find the tables. Open api/models.py and list five class names. Which one stores the people who log in? Which one connects a teacher to a student?
  4. Which program? For each, say which of the five programs does the work: (a) checking that a parent can't see another family's child, (b) writing the IEP text, (c) showing a red error banner, (d) remembering a student's date of birth.

  2. frontend/src/app/workspace/page.tsx, and frontend/src/app/students/[id]/reports/page.tsx.
  3. User stores accounts. StudentAccess links a user to a student (it has a user and a student foreign key). Others include Student, ReportCycle, GeneratedDocument, Notification, ActivityEvent.

Lesson 02: The Frontend Tour

You'll be able to: read a Next.js page top to bottom, find which file draws any URL, and spot the exact line where a page asks the backend for data.

Time: ~40 min · Open: frontend/src/app/students/[id]/page.tsx, frontend/src/lib/api.ts, frontend/src/context/AuthContext.tsx

We'll use one real page the whole way: the student profile page.

1. Folders are URLs (the App Router)

Next.js has a rule so simple it feels like a trick: the folder path under src/app/ is the URL, and the screen for that URL is the page.tsx inside it.

Folder in src/app/ URL in the browser
login/page.tsx /login
dashboard/page.tsx /dashboard
workspace/page.tsx /workspace
students/[id]/page.tsx /students/5, /students/42, …
students/[id]/reports/page.tsx /students/5/reports
admin/iep/page.tsx /admin/iep

Square brackets ([id]) mean "anything can go here, and capture it." One file handles /students/5 and /students/999, and the page can read which number was used (§4).

Debugging payoff: you find a screen's code by reading its URL. Broken thing at /students/5/reports? The file is frontend/src/app/students/[id]/reports/page.tsx. No searching needed.

Special filenames that sit next to page.tsx:

  • layout.tsx wraps pages. The root one, frontend/src/app/layout.tsx, wraps every page. students/[id]/layout.tsx wraps only the student pages.
  • globals.css holds app-wide styles and the color tokens (--accent-primary, etc.).

Heads-up, URLs with query strings: some screens switch content using ? parameters instead of folders. /workspace?workspace=reports&studentId=5 is still workspace/page.tsx. The page reads workspace and studentId and decides what to show. Folders pick the file; the ?… part is read inside the file.

2. "use client": the first line of almost every page

"use client";

This tells Next.js "run this component in the browser." Browser things like clicking, typing, useState, useEffect, and calling your API only work in client components.

The practical rule here: the pages you'll debug are client components. If you see a file without it and useState throws an error, that's why.

3. Read a component as a recipe

A React component is a function that returns what to show. Strip away the noise and every page looks like this:

export default function SomePage() {
  // 1. STATE: boxes holding values that can change
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);

  // 2. EFFECTS: code that runs at certain moments (like when the page first appears)
  useEffect(() => { /* go fetch data */ }, []);

  // 3. HANDLERS: functions that run when the user does something
  const handleClick = () => { /* ... */ };

  // 4. RETURN: the screen, written in JSX (HTML-ish)
  return <div>...</div>;
}

Lost on a page? Find those four parts and read them in order: state, effects, handlers, return. Now map them onto the real student page.

Note on file layout: students/[id]/page.tsx actually defines a component called StudentProfileContent (around line 90) and a small default export at the bottom that uses it. That's so the same profile can be shown inside the workspace too. When a page file feels split, look for export default. That's what the URL renders.

State: useState

const [data, setData] = useState<ProfileData | null>(null);
const [loading, setLoading] = useState(true);
const [error, setError] = useState("");

Read const [data, setData] = useState(null) as: "make a box called data, starting empty. To change it, call setData(...). When it changes, redraw the screen." That last part is the core of React: change the state and the screen updates by itself.

The trio data / loading / error shows up on nearly every page in ARASE. Learn it once, recognize it everywhere.

Effect: useEffect (where data gets fetched)

const fetchProfile = useCallback(async () => {
  try {
    const res = await api.get(`/api/students/${id}/profile/`);
    setData(res.data);
  } catch (err: any) {
    setError(err.response?.data?.error || "Failed to load profile.");
  } finally {
    setLoading(false);
  }
}, [id]);

useEffect(() => {
  if (user && id) {
    fetchProfile();
  }
}, [fetchProfile, id, user]);

Read slowly. This is the heart of the page:

  • useEffect(() => {...}, [deps]) means "run this after the page draws, and again whenever anything in [deps] changes." Here it waits until the user is known and there's an id.
  • api.get('/api/students/${id}/profile/') is the round trip. ${id} drops in the student number from the URL.
  • await means "wait for the server's answer before going on."
  • Success: setData(res.data) puts the answer in the box and the screen redraws.
  • Failure: setError(...). Note err.response?.data?.error. That's the "error" message the backend sent, shown as-is.
  • finally { setLoading(false) } stops the spinner either way.

This block is your best debugging anchor on any page. It names the exact backend URL the page depends on. If the page shows no data, you now know which endpoint to check.

Predict: what happens if user is null forever (say, the login cookie is broken)? (Answer at the bottom.)

Return: JSX

The return (...) at the bottom is the screen. It's HTML with two extras:

  • { } drops in a JavaScript value: {data.student.first_name}.
  • condition && <Thing/> shows <Thing/> only when the condition is true.

Debugging the look? Read the JSX. Debugging the data? Read the state and effect above it.

4. Reading the URL inside the page

const params = useParams();
const id = propStudentId || (params?.id as string);

useParams() gives you the captured pieces. For /students/5, params.id is "5" (a string, not a number). propStudentId || lets the workspace pass a student in directly instead of through the URL.

For ?query values, pages use useSearchParams() instead. Search the workspace page for it.

Open frontend/src/app/layout.tsx:

Mental model: the page is the filling, the layout is the sandwich. When every page breaks the same way (nobody stays logged in, no toasts anywhere), suspect a wrapper. When one page breaks, suspect that page.

Who's allowed on this page? ProtectedRoute

Many pages wrap themselves in components/ProtectedRoute.tsx:

<ProtectedRoute allowedRoles={['ADMIN']}> ... </ProtectedRoute>

It sends logged-out users to /login and wrong-role users to /dashboard. This is for convenience, not security. Someone could bypass it in their browser. The real check is on the backend (Lesson 03). Both should agree.

6. useAuth(): "who's logged in," anywhere

AuthContext.tsx uses React Context: a way to share one value with the whole app without passing it down by hand. Pages use it in one line:

const { user } = useAuth();

Now user is the logged-in person (or null). user.role decides which buttons to show; user.user_id is their id. The full shape is UserPayload in frontend/src/types/index.ts. Go read the field names. That's everything any page can know about the current user.

AuthContext also defines login, logout, and refreshUser. Lesson 04 traces login.

7. lib/api.ts: the single door to the backend

The most important non-page file in the frontend. You don't need all of it today, just these facts:

  1. One configured Axios client, exported as the default. Pages write import api from "@/lib/api", then api.get(...) / api.post(...). (Team rule: never use fetch for the backend. This file is why.)

  2. Where requests actually go depends on the environment:

    Where you are baseURL So api.get('/api/students/') hits…
    Local dev http://localhost:8000 Django directly
    Production '' (empty = same site) https://<the vercel site>/api/students/, which Next.js forwards to Railway

    That production forwarding is set up in frontend/next.config.ts (rewrites). Lesson 10 explains why it exists. It fixed a real login bug.

  3. withCredentials: true sends your login cookies with every request. That's how the backend knows who you are without the page ever touching a password or token.

  4. Two interceptors run on every request/response automatically:

    • Request: on writes (POST/PATCH/PUT/DELETE) it attaches the CSRF token header (X-CSRFToken), fetching one first if needed.
    • Response: on a 401 it quietly tries /api/auth/token/refresh/ once and retries the request. If that fails, it sends you to /login.

  5. At the bottom, buildWsUrl() builds the WebSocket address for live updates (Lesson 05).

Debugging payoff: "The app randomly kicks me to login" → that redirect is literally window.location.href = '/login' in the response interceptor. "Every save fails with a CSRF error" → the request interceptor. You know where to look instead of guessing.

Lesson 03: The Backend Tour

You'll be able to: answer "the frontend called /api/students/5/profile/, so what code runs, and where does the data come from?" for any endpoint in the app.

Time: ~45 min · Open: backend/urls.py, api/urls.py, api/views.py, api/models.py, api/serializers.py

1. The backend's job in one sentence

Get an HTTP request → figure out who's asking → check they're allowed → read or write the database → send back JSON.

Everything below is just where each step lives.

2. The order things run

When GET /api/students/5/profile/ arrives at daphne, Django runs this pipeline:

1. backend/urls.py        "Which app handles /api/...?"   → hands off to api/urls.py
2. api/urls.py            "Which view handles students/5/profile/?" → StudentProfileView
3. authentication         "Who is this?" reads the access_token cookie → sets request.user
                          (api/authentication.py → CookieJWTAuthentication)
4. permission + throttle  "Logged in? Too many requests?" (permission_classes, throttle rates)
5. the view method        get() / post() / … runs
       │
       ├─► api/services/*        the business logic
       │        └─► models       (api/models.py) ──► the database
       │
       └─► serializer            (api/serializers.py) turns rows into JSON
6. Response               JSON goes back to the browser

Keep this list nearby. When the backend misbehaves, ask "which of these six steps went wrong?" Each step is a specific file.

3. URLs: the switchboard

Top level: backend/urls.py

path('api/', include('api.urls')),

"Anything starting with /api/, go ask api/urls.py." This file also holds the auth endpoints directly (api/auth/token/, api/auth/me/, api/auth/logout/, api/auth/ws-ticket/, …), all pointing at api/auth_views.py. Notice many are listed twice, with and without a trailing slash. That matters (Lesson 09, case 1).

App level: api/urls.py

There are two styles here. Recognizing them saves a lot of confusion.

Style A: explicit path(...) for one-off endpoints

path('students/<int:student_id>/profile/', StudentProfileView.as_view(), name='student-profile'),

URL students/<a number>/profile/ → run StudentProfileView, and pass the number in as student_id.

Style B: a router for whole "resources" (ViewSets)

router = DefaultRouter()
router.register(r'students', StudentViewSet, basename='student')

That one line creates a whole family of URLs:

Method + URL What it does ViewSet method that runs
GET /api/students/ list students get_queryset → list
POST /api/students/ create a student create
GET /api/students/5/ get one retrieve
PATCH /api/students/5/ edit one partial_update
DELETE /api/students/5/ delete one destroy

Debugging payoff: if the frontend calls api.get('/api/students/'), don't search for that URL string. You won't find it. It comes from router.register('students', StudentViewSet). Go straight to StudentViewSet. For a specific path like /students/5/profile/, search api/urls.py for profile.

Order matters: in api/urls.py, the explicit students/<id>/... paths come before path('', include(router.urls)). Django uses the first match, top to bottom.

4. Views: the request handlers

ARASE uses two shapes.

Shape A: APIView (one endpoint, you write the methods)

StudentProfileView (search for it in views.py, around line 1440) is the whole pattern in a few lines:

class StudentProfileView(APIView):
    permission_classes = [permissions.IsAuthenticated]          # (a)

    def get(self, request, student_id):                         # (b)
        try:
            if request.user.role == 'ADMIN':                     # (c)
                student = Student.objects.get(id=student_id)
            else:
                student = Student.objects.get(id=student_id, assigned_users__user=request.user)
        except Student.DoesNotExist:
            return Response({"error": "Student not found or access denied."}, status=status.HTTP_404_NOT_FOUND)  # (d)

        from .services.student_service import get_student_profile_data
        return Response(get_student_profile_data(student, request.user))   # (e)

This is the template for reading any view:

  • (a) permission_classes: the gate. IsAuthenticated = "logged in, or get a 401."
  • (b) def get(self, request, student_id): the method name matches the HTTP verb. GET runs get, POST runs post. student_id came from the URL.
  • (c) the role check: security lives here, not in the frontend. Non-admins are limited by assigned_users__user=request.user (decoded in §5).
  • (d) error response: the "error" text here is exactly what the frontend's err.response?.data?.error shows on screen.
  • (e) the hand-off: the view doesn't build the profile. It calls a service.

Shape B: ViewSet (a whole resource at once)

StudentViewSet (top of views.py, line ~52). You don't write get/post; you override named methods:

class StudentViewSet(viewsets.ModelViewSet):
    serializer_class = StudentSerializer
    permission_classes = [permissions.IsAuthenticated]

    def get_queryset(self):                          # WHICH ROWS this user may see
        user = self.request.user
        ...
        if user.role == 'ADMIN':
            qs = Student.objects.all()
        else:
            # Non-admins only see students they've been explicitly assigned to via StudentAccess.
            qs = Student.objects.filter(assigned_users__user=user).distinct()
        return qs.alias(urgency=urgency_case).order_by('urgency', '-id')

    def create(self, request, *args, **kwargs):      # POST /api/students/
        if request.user.role != 'ADMIN':
            return Response({"error": "Only admins can register students."}, status=status.HTTP_403_FORBIDDEN)
        ...
        student, invitation = create_student_with_invitation(...)   # service does the work
        create_activity_event(event_type='STUDENT_CREATED', ...)     # tells live screens (Lesson 05)
        return Response(response_data, status=status.HTTP_201_CREATED, ...)

get_queryset is the most important method on a ViewSet. It decides which rows the user can even see. It's also used by retrieve, update, and destroy, so a student outside your queryset is a 404 for you no matter what. Most "why can't this user see that student?" bugs end here.

class StudentAccess(models.Model):
    user    = models.ForeignKey(User,    on_delete=models.CASCADE, related_name='student_access')
    student = models.ForeignKey(Student, on_delete=models.CASCADE, related_name='assigned_users')
  • A ForeignKey "points at one row in another table." Each StudentAccess links one User to one Student.
  • related_name='assigned_users' is the name for going backwards: from a student to its access rows, as student.assigned_users.
  • on_delete=models.CASCADE: delete the student, and its access rows go too.

That decodes the permission query: Student.objects.filter(assigned_users__user=request.user) means "students that have an access row whose user is me." The double underscore __ means "follow this relationship." That's the whole permission model for non-admins, and now you can read it.

Querying with .objects

You don't write SQL; you chain methods:

Code Meaning
Student.objects.all() every student
Student.objects.get(id=5) exactly one (raises DoesNotExist if 0, MultipleObjectsReturned if 2+)
Student.objects.filter(status='ENROLLED') zero or more
.exists() True/False: does anything match?
.first() the first match, or None (doesn't raise)
.order_by('-created_at') sort, newest first (- = descending)
status__in=[...] "status is one of these"

When you see SomeModel.objects.<something>, that line touches the database. Data bugs live there.

6. Serializers: rows ⇄ JSON

A database row isn't JSON. Serializers translate. Find StudentSerializer in api/serializers.py:

class StudentSerializer(serializers.ModelSerializer):
    has_parent_assessment = serializers.SerializerMethodField()   # COMPUTED, not a column
    next_action = serializers.SerializerMethodField()
    ...
    class Meta:
        model = Student
        fields = [
            'id', 'first_name', 'last_name', 'date_of_birth', 'grade', 'status',
            'has_parent_assessment', ..., 'next_action',
        ]

    def get_has_parent_assessment(self, obj):
        return ParentAssessment.objects.filter(student=obj).exists()

Three takeaways:

  • fields = [...] is the contract. Exactly these keys reach the frontend. If student.grade is undefined on screen, check that grade is in this list.
  • SerializerMethodField = computed on the fly by the matching get_<name> method. If a computed value looks wrong, read that method.
  • read_only_fields (see SelfUserSerializer, the one users edit their own profile through) = sent to the frontend, but the frontend can't change it. That's how role and grade_level stay admin-only. Admins edit users through a different one, AdminUserSerializer. One model can have several serializers, one per audience.

Worth noticing: each get_... method runs its own query, per student. A list of 100 students with 10 computed fields can be 1,000+ queries. If a list endpoint is slow, start here.

Not everything uses a serializer. MeView in auth_views.py builds its JSON by hand as a plain dict. A new user field has to be added there separately. Lesson 08 shows why that matters.

7. How the server knows who you are

You never send a password on each request, yet request.user is always set. How?

  1. At login, the server put your identity into a JWT (a signed token) and stored it in an HttpOnly cookie called access_token (JavaScript can't read it, so scripts can't steal it). There's also a longer-lived refresh_token cookie.
  2. The browser sends those cookies on every request (withCredentials: true in api.ts).
  3. settings.REST_FRAMEWORK['DEFAULT_AUTHENTICATION_CLASSES'] points at CookieJWTAuthentication in api/authentication.py. It reads the cookie, checks the signature, and sets request.user.
  4. On writes (POST/PATCH/DELETE) it also runs enforce_csrf(request). That's the server-side half of the CSRF header api.ts adds.

This explains a whole class of bugs: "I'm logged in but get a 401" almost always means the cookie didn't arrive or the token expired. "403 CSRF Failed" means the header and cookie don't match.

Lesson 04: Trace a Feature End to End

This is the most important lesson in the course. Everything before it was vocabulary. Here we follow two real features across both halves of the app, hop by hop, with exact files. Once you can do this yourself, you can debug almost anything in ARASE.

Time: ~45 min · Best done: with the app running and DevTools → Network open

We'll trace:

  • A. Logging in (a write: send a password, get a session). The cleanest full round trip.
  • B. Opening a student's profile (a read: fetch data and show it). The everyday pattern.

The skill we're practicing

Start at what the user did. Find the next file it calls. Repeat until you reach the database. Then follow the answer back. Each hop is one import or one URL.

That's it. No magic, just patiently asking "okay, what runs next?" In your editor, the move is: cursor on a name → F12 (Go to Definition). Lesson 06 has more shortcuts.

Trace A: Logging in

User action: types email and password on /login, clicks Sign In.

Hop 1: The page handler

File: frontend/src/app/login/page.tsx

The form's onSubmit runs handleLogin:

const { login } = useAuth();
...
const authenticatedUser = await login(email, password);

The page doesn't touch the network itself. It calls login(...), which came from useAuth(). So the next hop is AuthContext. (How do we know? useAuth is imported from @/context/AuthContext. Follow the import.)

Hop 2: The auth logic

File: frontend/src/context/AuthContext.tsx → login

const login = async (email: string, password: string) => {
  await fetchCsrfCookie();                                          // (i) get a CSRF token first
  const res = await api.post("/api/auth/token/", { email, password }); // (ii) THE round trip
  const basicUser = { user_id: res.data.user_id, role: res.data.role, email: res.data.email };
  setUser(basicUser);                                               // (iii) remember who's logged in
  const fullUser = await checkAuth();                               // (iv) fetch the full profile
  return fullUser || basicUser;
};

Line (ii) is the request leaving the browser. Next hop: api, i.e. lib/api.ts.

Hop 3: The door

File: frontend/src/lib/api.ts

api.post goes through the request interceptor, which adds the X-CSRFToken header because it's a POST. Then it's sent with cookies (withCredentials):

Local:       POST http://localhost:8000/api/auth/token/      body: { email, password }
Production:  POST https://<vercel site>/api/auth/token/      → next.config.ts forwards it to Railway

We've crossed the wire. The request has left the frontend.

Hop 4: The server's switchboard

File: backend/urls.py

path('api/auth/token/', CookieTokenObtainPairView.as_view(), name='token_obtain_pair'),

Hop 5: The login view

File: api/auth_views.py → CookieTokenObtainPairView.post

def post(self, request, *args, **kwargs):
    serializer = self.get_serializer(data=request.data)
    try:
        serializer.is_valid(raise_exception=True)          # (a) check email + password
    except TokenError as e:
        raise InvalidToken(e.args[0])

    access = serializer.validated_data['access']           # (b) signed tokens
    refresh = serializer.validated_data['refresh']
    user = serializer.user

    response = Response({'user_id': user.id, 'role': user.role, 'email': user.email,
                         'message': 'Login successful.'}, status=status.HTTP_200_OK)
    return _set_auth_cookies(response, access, refresh)    # (c) tokens go into HttpOnly cookies
  • (a) The check happens in CustomTokenObtainPairSerializer in serializers.py. It finds the user by email ignoring capitals (email__iexact), then SimpleJWT compares the password against the hashed one in the User table. Wrong password → 401 → the page's catch shows "Invalid credentials" (or the backend's detail message).
  • (b) On success, two tokens: short-lived access, longer-lived refresh. The serializer's get_token also puts role inside the token.
  • (c) _set_auth_cookies sets them as HttpOnly cookies. The JSON body never contains the raw tokens. In production the cookies are Secure and SameSite=None; in dev they're SameSite=Lax.

Hop 6: The answer comes back

Back in Hop 2: res.data is { user_id, role, email, message }. setUser(basicUser) stores it. Because AuthProvider wraps the whole app, every page now knows who's logged in.

Hop 7: Fetch the full profile (a mini round trip)

checkAuth() calls api.get("/api/auth/me/"). Same journey: api.ts → backend/urls.py → MeView.get in auth_views.py. It reads request.user (identified from the cookie that was just set) and returns a hand-built dict: names, phone, specialties, grade_level, languages, onboarding/profile completeness. setUser runs again with the richer data.

Hop 8: Redirect by role

Back in login/page.tsx:

const landingRoute = authenticatedUser.role === "SPECIALIST" && authenticatedUser.specialist_onboarding_complete === false
  ? "/specialist-onboarding"
  : authenticatedUser.role === "ADMIN"
    ? "/dashboard"
    : ["TEACHER", "SPECIALIST"].includes(authenticatedUser.role)
      ? "/workspace"
      : "/dashboard";
router.push(landingRoute);

Notice this needs specialist_onboarding_complete, which only /api/auth/me/ returns. That's why Hop 7 exists.

Lesson 05: Background Jobs & Live Updates

You'll be able to: follow an IEP generation from the button, through the Celery worker and Gemini, and back to the screen, and explain the two ways the screen finds out it's done.

Time: ~45 min · Open: frontend/src/app/admin/reports/page.tsx, api/tasks.py, api/services/realtime_service.py, frontend/src/components/RealtimeProvider.tsx

1. Why the simple round trip isn't enough

Lesson 04's round trips finish in under a second. Writing an IEP with AI can take 30 seconds or more. If the backend did that inside the request:

  • the browser would sit waiting, and might give up (time out),
  • that server process couldn't answer anyone else meanwhile,
  • if the AI call failed halfway, nobody would hear about it.

So ARASE splits slow work in two:

  1. "Please start"   browser ──► backend: queue the job, answer "202 Accepted, here's a task_id"   (fast)
  2. The work         Celery worker picks up the job, calls Gemini, saves the IEP                    (slow)
  3. "It's done"      the screen finds out, two ways at once:
                        a) POLLING:   the page asks "done yet?" every 3 seconds
                        b) PUSH:      the server sends a WebSocket message the moment it's saved

Three new pieces show up here:

Piece What it is Where
Celery A separate Python program (the "worker") that runs jobs from a queue api/tasks.py, backend/celery.py
Redis The queue between the backend and the worker. Also carries live messages between processes in production. installed separately; REDIS_URL
WebSocket A connection that stays open so the server can send to the browser without being asked api/consumers.py, RealtimeProvider.tsx

2. Trace C: Generate an IEP

User action: an admin clicks Generate IEP on a student's reports screen.

Hop 1: The button

File: frontend/src/app/admin/reports/page.tsx → handleGenerateIEP

const res = await api.post("/api/iep/generate/", {
  student_id: studentId,
  report_cycle_id: reportCycleId,
});
if (res.data.task_id) {
  pollTaskStatus(res.data.task_id,
    (result) => openGeneratedDocument("iep", result.doc_id),
    (err) => { setErrorMsg(err); setLoading(false); }
  );
} else {
  openGeneratedDocument("iep", res.data.iep_id);   // it already existed
}

Two possible answers: a task_id (job started) or an iep_id (an IEP for this cycle already exists, so just open it).

Hop 2: The view checks, then queues

File: api/views.py → GenerateIEPView.post (~line 2280)

Read it top to bottom. It's a stack of guards, each of which can stop the request early:

if request.user.role != 'ADMIN':                       → 403 "Only admins can generate IEPs."
if not student_id or not report_cycle_id:              → 400
Student / ReportCycle not found:                       → 404
existing_iep found:                                    → 200 { iep_id }   (no new job)
no parent assessment, or specialist one not finalized: → 400 "...are required before generating an IEP."

Only if every guard passes:

create_activity_event(event_type='REPORT_QUEUED', ...)          # tell live screens "queued"
try:
    task = generate_iep_task.delay(student_id, report_cycle_id, request.user.id)   # ← drop job in Redis
except Exception as exc:
    return Response({"error": "Background worker is unavailable. Start Redis and a Celery worker, then try again."},
                    status=status.HTTP_503_SERVICE_UNAVAILABLE)
return Response({"message": "IEP generation started.", "task_id": task.id}, status=status.HTTP_202_ACCEPTED)

.delay(...) is the key. It doesn't run the function. It writes "please run generate_iep_task with these arguments" into Redis and returns at once with a task id. 202 Accepted means "got it, working on it," not "done."

Predict: Redis is running, but nobody started the Celery worker. What does the admin see? (Answer at the bottom. This one really happens.)

Hop 3: The worker picks it up

File: api/tasks.py → generate_iep_task

A different program now: the Celery worker you started in terminal 3. It's been watching Redis, sees the job, and runs:

@shared_task(bind=True, max_retries=2, default_retry_delay=30)
def generate_iep_task(self, student_id, cycle_id, user_id=None):
    try:
        doc, iep_data = run_iep_generation(student_id, cycle_id)      # the real work
        record_document_version(doc, user, 'GENERATED')               # audit trail
        create_activity_event(event_type='REPORT_READY', ...)          # tell live screens "ready"
        notify_iep_finalized(doc.student, doc.id)                     # bell notifications
        return {'doc_id': doc.id, 'status': 'completed'}               # ← what polling will read
    except Exception as exc:
        _notify_generation_failed(student_id, "IEP generation failed", exc, 'IEP', user_id)
        raise self.retry(exc=exc)                                      # try again in 30s, up to 2 more times

Two things worth noticing:

  • Its prints and errors show up in the Celery terminal, not daphne's. Different program, different terminal.
  • It retries. A Gemini hiccup doesn't fail the whole thing right away.

Hop 4: The service does the work

File: api/services/iep_service.py → run_iep_generation

  1. Load the student and cycle. If an IEP already exists, return it (no duplicates).
  2. collect_iep_inputs(...): gather the parent assessment, specialist assessment, and diagnostic report text.
  3. generate_iep(...) in api/iep_generator.py: build a long prompt, send it to the AI.
  4. Render the PDF first, then create the GeneratedDocument row. (The comment explains why: anyone refreshing mid-generation sees either no IEP or a complete one, never half.)

Hop 5: The AI call

iep_generator._call_gemini → gemini_service.call_gemini_json → llm_service.call_json. llm_service.py reads AI_PROVIDER:

AI_PROVIDER What happens
gemini Google Gemini only. Needs GEMINI_API_KEY.
ollama A local model at OLLAMA_BASE_URL. Free and offline, but much weaker.
auto Try Gemini; if it fails, fall back to Ollama. (The team's dev setting.)

The AI must answer in JSON. _parse_json_response cleans it up (strips ``` fences). A garbled answer fails here, and that's a common source of "generation failed."

Hop 6a: The page finds out by POLLING

Back in admin/reports/page.tsx, pollTaskStatus has been asking every 3 seconds:

const res = await api.get(`/api/tasks/${taskId}/status/`);
if (res.data.status === "SUCCESS")  { clearInterval(interval); onSuccess(res.data.result); }
else if (res.data.status === "FAILURE") { clearInterval(interval); onError(res.data.error || "Background task failed."); }

That hits TaskStatusView (api/views.py, ~line 2987), which asks Celery about the task (AsyncResult(task_id)). Results are stored in the database (CELERY_RESULT_BACKEND = 'django-db'), so the backend can read what the worker wrote. On SUCCESS, result is the dict the task returned: {'doc_id': ...}. The page opens it.

Hop 6b: The page finds out by PUSH (WebSocket)

At the same time, the REPORT_READY event from Hop 3 travels a completely different road:

tasks.py   create_activity_event('REPORT_READY', student=...)
              │  saves an ActivityEvent row, then after the DB commit:
              ▼
realtime_service._broadcast()
              │  picks "refresh targets" for this event type: dashboard, workspace, student, reports
              │  sends to channel-layer GROUPS:
              │     realtime_admins                  every admin's socket
              │     realtime_user_<id>               each user assigned to the student (if visibility = STUDENT_TEAM)
              ▼
consumers.RealtimeConsumer.realtime_event()   (running inside daphne, one per open browser tab)
              │  ws.send(JSON)
              ▼
RealtimeProvider.tsx   ws.onmessage
              │  dispatchRealtimeMessage(message)  → fires a browser event 'arase:realtime-event'
              │  showRealtimeToast(message)        → "IEP ready for ..." pop-up
              ▼
useRealtimeRefresh({ targets: ['reports', 'workspace', 'student'], onRefresh: fetchReportProfile })
              │  "is this event for a target I care about, and for my student?" → yes
              ▼
fetchReportProfile()   a normal api.get → the page refetches and shows the new IEP

The key design idea, written right in RealtimeConsumer's docstring: the WebSocket only says "something changed." The REST API is still the source of truth. Pages always refetch with a normal api.get. They never trust data inside the push.

Why both? Polling only helps the one tab that clicked the button. Push updates everyone: the other admin looking at the dashboard, the teacher's workspace. And polling is the safety net when push doesn't arrive (see §4).

3. How the WebSocket connects

RealtimeProvider.tsx wraps every page (Lesson 02 §5), so it opens one socket per tab:

  1. buildWsUrl('/ws/realtime/') in api.ts first calls GET /api/auth/ws-ticket/ for a 60-second token, then builds ws://localhost:8000/ws/realtime/?token=.... (Why not the cookie? In production the page and the backend are on different domains and WebSockets can't go through the Vercel proxy. Lesson 09, case 2.)
  2. daphne gets the connection. backend/asgi.py sends WebSocket traffic to api/routing.py → RealtimeConsumer.
  3. connect() checks the token, then joins groups: realtime_user_<my id>, plus realtime_admins for admins.
  4. If the socket drops, onclose reconnects after a delay.

Other sockets work the same way: /ws/notifications/ (the bell, NotificationConsumer) and the collaboration socket for shared form editing (CollaborationConsumer, used by hooks/useFormCollaboration.ts).

4. The dev gotcha: two processes can't hear each other without Redis

Messages between groups go through the channel layer. Look at backend/settings/dev.py:

if not os.environ.get('REDIS_URL'):
    CHANNEL_LAYERS = {'default': {'BACKEND': 'channels.layers.InMemoryChannelLayer'}}

"In memory" means inside one program's memory. daphne and the Celery worker are two separate programs. So locally, without REDIS_URL in your .env:

Event created in… Reaches the browser?
a view (inside daphne), e.g. STUDENT_CREATED, REPORT_QUEUED Yes. Same program as the sockets.
a Celery task, e.g. REPORT_READY, REPORT_FAILED No. It's sent into the worker's own memory and nobody's listening.

That's exactly why polling matters locally: the IEP still opens because Hop 6a works. But other tabs won't live-update. In production, both processes use Redis, so pushes from the worker arrive.

If you're debugging live updates from a task locally, set REDIS_URL=redis://localhost:6379/0 in .env and restart daphne and the worker.

5. The other background job: translation

Not everything starts from a button. At the bottom of api/models.py:

for model in [ParentAssessment, MultidisciplinaryAssessment, SpedAssessment,
              ParentProgressTracker, MultidisciplinaryProgressTracker, SpedProgressTracker]:
    post_save.connect(trigger_translation_task, sender=model)

A signal: "every time one of these is saved, call trigger_translation_task." That queues translate_form_data_task in Celery, which translates the answers (parents may write in Tagalog or other languages) into translated_data.

Two traps it guards against:

  • Infinite loop: the task saves the form again, which would fire the signal again. The if update_fields and 'translated_data' in update_fields: return check stops that.
  • Invisible code: nothing in views.py mentions translation. If you're wondering "what else happens when a form is saved?", search for post_save.

Lesson 06: Reading Big Files Without Drowning

You'll be able to: find what you need in api/views.py (3,400 lines) or frontend/src/app/workspace/page.tsx (4,400 lines) in seconds, by jumping instead of scrolling.

Time: ~30 min · Open: VS Code with the project

The mindset shift

A 3,400-line file is not a 3,400-line problem. views.py is about 100 small, separate classes stored in one file. You only need the one that matters for your task. The skill is finding it in seconds and ignoring the rest without guilt.

Nobody reads big files top to bottom. Not even whoever wrote them. They navigate.

The six moves (learn these shortcuts)

VS Code defaults on Windows. On Mac, use Cmd instead of Ctrl.

Move Shortcut Use it to…
Go to symbol in file Ctrl+Shift+O Jump to any class/function in this file by name
Go to symbol anywhere Ctrl+T Jump to a class/function in any file (StudentProfileView)
Open file by name Ctrl+P Type views or student_service and press Enter
Search the project Ctrl+Shift+F Find a string everywhere: an error message, a URL, a function name
Go to definition / find uses F12 / Shift+F12 Follow a hop: cursor on login → F12 → you're in AuthContext.tsx
Go back Alt+← Return to where you were after jumping (like a browser Back button)

Try it now: open api/views.py, press Ctrl+Shift+O, type StudentProfile, press Enter. You just crossed a 3,400-line file in two seconds.

Also keep the Outline panel open (Explorer sidebar, bottom). For views.py it's basically a menu of every endpoint in the app.

Error messages are addresses

This is the single most useful trick in the lesson.

Every error the user sees was typed by someone, somewhere. Copy the exact words from the screen or the Network tab's Response, then Ctrl+Shift+F:

  • "Only admins can register students." → api/views.py, StudentViewSet.create
  • "Background worker is unavailable…" → GenerateIEPView.post
  • "Failed to load profile." → frontend/src/app/students/[id]/page.tsx (a frontend fallback, which tells you the backend didn't send its own message)

Search for a distinctive chunk (4–6 words), not the whole sentence, in case part of it is built from variables.

Use the structure the file already has

views.py has section banners

# ─── Students ────────────────────────────────────────
class StudentViewSet(viewsets.ModelViewSet): ...

# ─── Student Profile ─────────────────────────────────
class StudentProfileView(APIView): ...

# ─── IEP Generation & Management ─────────────────────
class GenerateIEPView(APIView): ...

Ctrl+F for # ─── and press Enter repeatedly. You'll skim the whole file's table of contents in ten seconds: Students, Users, Form Input ViewSets, Section-scoped writes, Parent Onboarding, Student Profile, Dashboard Actions, Student Actions, Staff, Report Generation, Invitations, SMS Verification, IEP, Monthly Report, Audit Logs, Cycle Management, Notifications…

api/urls.py is the index

It's short and lists every endpoint next to its view. When lost in views.py, start in urls.py. Find the URL, read the view name, then Ctrl+Shift+O to it. urls.py is the index; views.py is the book.

Watch for base classes

Some views are tiny because they inherit from a bigger one:

class AssessmentSectionWriteView(SectionWriteView):
    ...  # just a few lines

If a view looks empty, the logic is in its parent (SectionWriteView). F12 on the parent name. BaseInputViewSet does the same for all the form ViewSets.

The giant frontend file: workspace/page.tsx

This one's harder. Almost all of it is one function, UnifiedWorkspaceContent, from line ~258 to ~4,380, with ~40 useState calls. Strategies:

  1. Find what it fetches. Ctrl+F for api. and step through the matches (~16). Each is a backend endpoint the workspace depends on. That's your list of "where the data comes from."
  2. Find how it picks what to show. It's driven by the URL's query string. Ctrl+F for searchParams.get(: studentId, workspace, view, tab, docId, teamRole. When a bug only happens on one view, find where that param is read and follow the variable.
  3. Fold everything. Ctrl+K Ctrl+0 folds all blocks. Then unfold only the part you need. Ctrl+K Ctrl+J unfolds everything again.
  4. Search for the visible text. See a heading "Teacher Progress" on screen? Search for it. You land in the JSX that draws it. (Here it's in the TABS list near the top.)
  5. Check the imports at the top. The workspace embeds whole other pages: StudentProfileContent (from students/[id]/page), FormEntryContent (from forms/[type]/page), AdminReportsContent, IEPViewerContent, MonthlyReportContent, ParentFormContent. If a bug is inside one of those sections, the code lives in that other file, not in the workspace. This trips people up constantly.

How to read ONE function once you've found it

Don't read every line yet. Answer three questions, in order:

  1. What goes in? The signature: def get(self, request, student_id):. Inputs: request (who's asking, what they sent) and student_id (from the URL).
  2. What comes out? Find every return. In a view, each return Response(...) is a possible outcome. Early returns are the guards: read those first; they list the ways it can say no.
  3. What does it call? Scan for something_service.func(...), Model.objects..., .delay(...). Those are the next hops. Decide if you need to follow them, or if "it calls the student service" is enough for now.

Most of the time you don't need to understand the middle. Inputs, outputs, and hand-offs are 90% of debugging.

Worked example: "where does the admin dashboard's action list come from?"

  1. Admins render dashboard/AdminDashboard.tsx (Lesson 02). Ctrl+F for api.get → api.get("/api/dashboard/actions/").
  2. Ctrl+Shift+F for dashboard/actions → api/urls.py: path('dashboard/actions/', AdminDashboardActionsView.as_view(), ...).
  3. Ctrl+T → AdminDashboardActionsView. Read its guards, then what it queries and returns.
  4. Done. You answered a question about a 3,400-line file by reading maybe 30 lines of it.

You're not reading the file. You're querying it.

When a function really is too tangled

AdminDashboardActionsView and the workspace are genuinely meaty. Tactics:

  • Comments and early returns first. They summarize intent and edge cases.
  • Print the value instead of reasoning about it. One print(...) or console.log(...) beats ten minutes of guessing (Lesson 07). Remove it after.
  • Understand locally, not globally. If you've found where the bug is, you can often fix it without understanding every other branch.
  • Ask AI about one function, not the file. Paste the 40 lines you've narrowed down, plus the error. You'll get a far better answer than "explain views.py."

Lesson 07: The Debugging Playbook

You'll be able to: take any "it's broken" report and narrow it to one file, using a fixed method and the right tool for each question.

Time: ~45 min · Best done: with the app running and DevTools open (F12 in the browser)

The big secret: debugging isn't guessing, and it isn't staring at code hoping. It's narrowing down: cutting the problem in half until one suspect is left. You already have the map (Lesson 04's hops). This lesson is the method for walking it backwards from a symptom.

Step 0: Is the code you're testing actually running?

Before anything else, especially if "I already fixed this":

  • Changed a .py file? Restart daphne. It doesn't reload by itself.
  • Changed api/tasks.py or api/services/*? Restart the Celery worker too.
  • Changed a model? Run python manage.py makemigrations and migrate, then restart.
  • Changed frontend code? It hot-reloads. If it looks stuck, hard refresh (Ctrl+Shift+R).

This one step solves a surprising share of "it still doesn't work."

The 5-step method (in order, every time)

Step 1: Reproduce it exactly

Find the exact clicks that cause it, every time. Note who (which role, which account), which student, and what you expected vs. what happened. If it's intermittent, note what's different when it happens. Don't start fixing until you can make it happen on demand.

Step 2: Read the error. Actually read it.

The #1 beginner mistake is skimming past the error. It usually tells you the file and line. Errors show up in four places. Check the right one:

Where What shows up there
Browser Console Frontend crashes, your console.logs
Browser Network tab Every request, its status code, what was sent, what came back
daphne terminal Backend crashes (tracebacks), your prints from views and services
Celery terminal Background-job crashes, prints from tasks and anything they call

Step 3: Which program?

Open the Network tab, reproduce, and look at the request:

  • No request sent when you clicked → frontend bug (handler not wired, JS error before the call, or an effect that never fired). Check the Console.
  • Request sent, came back red (4xx/5xx) → backend refused or crashed. The status code says which (cheat sheet below).
  • Request OK (2xx) but the screen is wrong → compare Response to the screen. Data wrong in Response → backend (service/serializer). Data right in Response → frontend rendering.
  • 202, then nothing ever happens → background job. Check the Celery terminal. Is the worker even running?

Step 4: Narrow to one hop

You know the program. Now find the hop using Lesson 04's chain. Put one console.log / print at a hop and check the value. As expected? Move one hop later. Not as expected? The bug is at this hop or the one before. This is binary search on your own code.

Step 5: Fix the smallest thing, then check again

Change one thing. Re-run Step 1 exactly. Fixed, and nothing else broke? Resist fixing five things at once. You won't know which one worked.

Tool 1: Browser DevTools (F12)

Console tab

  • Red errors = frontend crashes. Read the top line (what) and the file:line link (where). Click the link.
  • Classic: Cannot read properties of undefined (reading 'first_name'). You wrote data.student.first_name but data.student was undefined: the data hadn't arrived, or the key name is wrong.

Network tab (your best tool)

  1. Open it, then reproduce. Each row is one request.
  2. Filter by Fetch/XHR. Type part of the URL (e.g. profile) in the filter box.
  3. Read the Status column.
  4. Click the row:
    • Headers: the full URL, the method, and whether cookies were sent (Cookie: line).
    • Payload: exactly what the frontend sent. ("Did I send the right data?")
    • Response: exactly what came back. (The real data, or the error message.)
  5. For live updates, filter by WS, click the realtime/ row, open Messages. You'll see each pushed event arrive.

Application tab → Cookies

Look for access_token, refresh_token, and csrftoken. Missing auth cookies explain almost every "keeps logging me out" bug.

Status codes: what they mean in ARASE

Code Name Here it usually means Where to look
200 OK Worked (Response tab, if the data's wrong)
201 Created A POST created something
202 Accepted A background job was queued, not finished Celery terminal
204 No Content Worked, nothing to return (often DELETE)
400 Bad Request Frontend sent missing/invalid data, or a guard said "not ready yet" Response says which field; the view's guards; serializer validation

Tool 2: Reading a Python traceback (for 500s)

On a 500, the real story is in the daphne terminal (or the Celery terminal for a background job). Django prints a traceback: the chain of calls that led to the crash.

Read it from the bottom up:

Traceback (most recent call last):
  File ".../django/core/handlers/exception.py", line 55, in inner     ← framework, skip
  ...
  File "C:\...\030625\api\views.py", line 1447, in get                 ← YOUR CODE: where
    student = Student.objects.get(id=student_id, ...)
  File ".../django/db/models/query.py", line 649, in get              ← framework, skip
    raise self.model.DoesNotExist(
api.models.Student.DoesNotExist: Student matching query does not exist.   ← WHAT went wrong
  • The last line is what broke (exception type + message).
  • The lowest line that points at your files (api\..., not django\... or site-packages) is where in your code. Open that file at that line.

Common exception names, translated: DoesNotExist = .get() found nothing · KeyError: 'x' = a dict had no key 'x' · AttributeError: 'NoneType' object has no attribute 'y' = something was None that you expected to be an object · IntegrityError = the database refused (duplicate, or a required field missing) · OperationalError: no such column = you forgot to migrate.

Tool 3: print() / console.log()

You don't need fancy tools to see a value. Print it.

  • Python: print("HERE", student_id, request.user.role). Shows in the daphne terminal (or Celery's, if it runs in a task). The code also uses logger.info(...) / logger.error(...), which work the same way.
  • TypeScript: console.log("data is", data). Shows in the browser Console.

Use it to replace an assumption with a fact at each hop: Is student_id really 5 here? Is data actually null? Did this line even run? Half of all bugs are "the value isn't what I thought." Remove your prints when done.

Tool 4: Breakpoints (when prints aren't enough)

A breakpoint pauses the program so you can look at everything at that moment.

  • Frontend: DevTools → Sources, click a line number. Or write debugger; in the code.
  • Backend: add breakpoint() on a line. When that line runs, the daphne terminal becomes an interactive prompt. Type a variable name to see it, n for next line, c to continue. (This freezes the server for everyone until you continue. Fine locally, never in production.)

Prints are faster for "what is this one value." Breakpoints win for "let me look at everything right here."

Tool 5: The Django shell (look at the data directly)

Sometimes the code is fine and the data is the surprise. Ask the database directly:

python manage.py shell

"Is this teacher actually assigned to this student?" takes ten seconds this way. Read freely; be very careful about changing data here. There's no undo.

Lesson 08: Making a Change Safely

You'll be able to: add a new piece of data all the way from the database to the screen, know every file it touches, and check you didn't break anything before you commit.

Time: ~40 min · Open: api/models.py, api/serializers.py, api/auth_views.py, frontend/src/types/index.ts

Reading code is half the job. The other half is changing it without surprises. We'll study a real change from this repo's history: adding a teacher's grade_level (commit a35b4f0, August 2026).

1. The real example: "teachers have a grade level"

The goal: admins assign each teacher a grade level, so students can be matched to teachers. Teachers can see theirs but not change it.

Here's every place it had to go. This list is the lesson.

 BACKEND                                                FRONTEND
 ───────                                                ────────
 1. api/models.py          add the column               6. src/types/index.ts     add it to the TS shapes
 2. api/migrations/0053_…  tell the DB about it         7. pages that show/edit it (users/[id], dashboard, …)
 3. api/serializers.py     expose it in JSON
 4. api/auth_views.py      add it to /api/auth/me/
 5. validation             api/grade_levels.py

Step 1: The model

class User(AbstractUser):
    ...
    grade_level = models.CharField(
        max_length=50,
        blank=True,
        default='',
        help_text="The grade level a teacher handles. Assigned by admin, used for student matching.",
    )

blank=True, default='' matters: existing users don't have a value, so the column must allow empty. Add a required field with no default and the migration will stop and ask you what to put in the existing rows.

Step 2: The migration

python manage.py makemigrations
python manage.py migrate

makemigrations compares your models to the migration history and writes a new file, here api/migrations/0053_invitation_grade_level_user_grade_level.py:

operations = [
    migrations.AddField(model_name='invitation', name='grade_level', field=models.CharField(...)),
    migrations.AddField(model_name='user',       name='grade_level', field=models.CharField(...)),
]

migrate applies it to your local db.sqlite3. Production applies it on deploy (the Railway start command runs migrate). Commit the migration file with the model change.

Migration rules: never edit or delete a migration that's already been committed and deployed. Never hand-write one for a simple field. Let Django generate it. If two people both add migrations at once, you'll get two 0055_… files. Django will tell you, and makemigrations --merge fixes it.

Step 3: The serializers

A new column is invisible to the frontend until a serializer lists it (Lesson 03 §6). It was added to two:

class AdminUserSerializer(...):   # admins editing any user
    fields = [..., 'specialties', 'grade_level', 'languages', ...]

class SelfUserSerializer(...):    # a user editing themselves
    fields = [..., 'grade_level', ...]
    # Grade levels sit with specialty: admin-assigned, never self-editable.
    read_only_fields = [..., 'grade_level', ...]

That read_only_fields line is the security part: a teacher sending PATCH { grade_level: "Grade 6" } for themselves gets it silently ignored. The frontend hiding the input is not enough (Lesson 01 §2).

Step 4: The hand-built /me endpoint (the easy one to miss)

MeView doesn't use a serializer. It builds its dict by hand:

return Response({
    'user_id': user.id,
    ...
    'grade_level': getattr(user, 'grade_level', '') or '',
    ...
})

Miss this and everything seems fine on admin screens, but useAuth().user.grade_level is always undefined. When adding a user field, always search auth_views.py too.

Step 5: Validation

Admins type grade levels, and Student.grade is free text ("Grade 3", "3", "gr 3"). So a shared normalizer was added, with one copy per language:

  • api/grade_levels.py → validate_grade_level(...), called from the serializers
  • frontend/src/lib/grade-levels.ts → normalizeGradeLevel(...), used by the UI

If you change the rules in one, change the other, or the screen and the server will disagree.

Step 6: TypeScript types

export interface UserPayload { ...; grade_level?: string; ... }   // what useAuth() holds
export interface UserProfile { ...; grade_level?: string; ... }   // a user from /api/users/

Types don't do anything at runtime. They make your editor warn you when you use a field wrong. Add the field and you get autocomplete everywhere.

Step 7: The screens

Finally, the UI: the admin edits it on users/[id]/page.tsx (api.patch(\/api/users/${id}/`, { grade_level: gradeLevel })`), and dashboards show it.

2. The general recipes

Adding a field

  1. Model (api/models.py), with blank=True / null=True / default= for existing rows
  2. makemigrations → read the generated file → migrate
  3. Every serializer that should expose it (Ctrl+Shift+F for model = YourModel)
  4. Any hand-built dicts: MeView, get_student_profile_data, other services returning dicts
  5. read_only_fields if users mustn't change it
  6. TypeScript types in frontend/src/types/
  7. The UI
  8. Restart daphne (and Celery if tasks use it)

Adding an endpoint

  1. A view in api/views.py, under the right # ─── banner. Start with permission_classes and the role check, then the logic.
  2. Put real logic in a service in api/services/, not the view.
  3. Add the URL in api/urls.py. End it with /. All ARASE URLs have a trailing slash.
  4. Import the view at the top of api/urls.py (the big import list).
  5. Call it from the frontend with api.get/post(...), never fetch.
  6. If other screens should update live, call create_activity_event(...) (Lesson 05).
  7. Restart daphne.

Changing something that already exists

Before you change a function, find everyone who uses it: cursor on its name → Shift+F12, or Ctrl+Shift+F. The bigger that list, the more careful you need to be.

4. Breaking changes: what to warn the team about

Some changes break things other people depend on. Flag these before merging:

  • Renaming or removing a field in a serializer or a hand-built dict. The frontend reads it by name.
  • Changing a URL. Every api.get('...') using it breaks.
  • Changing a status code or error message. The frontend may check for it.
  • Migrations that delete or rename columns. The data is gone after deploy.
  • New environment variables. Production won't have them until someone adds them on Railway/Vercel (Lesson 10).

Lesson 09: Real Bugs Casebook

You'll be able to: recognize bug patterns that already happened in ARASE, and know the first place to look when one shows up again.

Time: ~40 min · Open: a terminal for git show <commit>

Every case here is real. It happened in this app, and the commit that fixed it is in git log. For each one: read the symptom, then stop and guess where you'd look before reading on. Then check the fix yourself:

git show de268bf

The commit messages are written to explain why, so they're worth reading in full.

Case 1: "Login works, but every dashboard is empty"

Commit: de268bf · Where it showed up: production only

Symptom: You could log in fine, but dashboards loaded with no data. No red error on screen.

Clues you'd have seen: Network tab full of 301 redirects bouncing between the same URLs, over and over, for every data request. Auth requests (/api/auth/token/, /me/) were fine.

What was wrong: In production the browser calls the Vercel site, and next.config.ts forwards /api/* to Railway (Lesson 10). The rewrite rule /api/:path* → .../api/:path* dropped the trailing slash. Django has APPEND_SLASH on: it answered /api/students with "301, go to /api/students/". The browser went there, Vercel stripped the slash again, Django redirected again… forever.

Why did login still work? Look at backend/urls.py: the auth routes are listed twice, with and without a slash (api/auth/token and api/auth/token/). The data routes in api/urls.py only have the slash version.

The fix: one character in frontend/next.config.ts:

// :path* drops the trailing slash; Django needs it or it 301s back here in a loop.
destination: `${baseUrl}/api/:path*/`,

The pattern: "Some requests work and others don't" → find what's different between them. Here it was the slash. Also: a 301 loop in the Network tab = a URL rewriting problem, not a code bug.

Case 2: "Login fails in incognito and on Safari"

Commit: c1362d8 · Where: production only

Symptom: Login worked in normal Chrome. In incognito or Safari, you clicked Sign In and just… stayed logged out. Sometimes it went to the dashboard and bounced back to /login.

Clues: POST /api/auth/token/ returned 200 with Set-Cookie headers. But DevTools → Application → Cookies showed no access_token. The next request (/api/auth/me/) got 401.

What was wrong: The frontend lived on *.vercel.app, the backend on *.railway.app, which are different sites. Cookies set by Railway were third-party cookies from the page's point of view. Incognito and Safari block those by default. The server set the cookie; the browser threw it away.

The fix: make the browser talk only to its own site. In production, api.ts now uses an empty baseURL (same site), and next.config.ts forwards /api/* to Railway behind the scenes. Cookies are now first-party. (This is the rewrite that caused Case 1!)

But WebSockets can't go through that forwarding, so they still connect to Railway directly, and that connection doesn't get the cookie anymore. So a new endpoint, /api/auth/ws-ticket/ (WsTicketView in auth_views.py), hands out a 60-second token, and buildWsUrl() in api.ts passes it as ?token=....

The pattern: "Works in one browser, not another" → cookies, storage, or privacy settings. Check the Application → Cookies tab before reading any code. Also: fixes create new edge cases. This fix directly led to Case 1.

Case 3: "Parents got a red 'IEP generation failed' toast"

Commit: 8b4b792

Symptom: When an AI generation failed (e.g. a bad API key), the family saw a red error toast about it. An internal problem, shown to the wrong people.

What was wrong: In api/tasks.py, the failure path called create_activity_event(...) with student=student and no visibility. Look at create_activity_event in realtime_service.py:

resolved_visibility = visibility or ("STUDENT_TEAM" if student else "ADMINS")

A student was attached, so it defaulted to STUDENT_TEAM, and _broadcast sends those to every user with a StudentAccess row for that student. Parents included.

The fix: one helper, _notify_generation_failed, used by all three generation tasks. It keeps the student (for context) but forces visibility='ADMINS', and sends it directly to the staff member who clicked, who might not be an admin.

The pattern: Defaults are decisions. A function that "picks a sensible default" can pick the wrong one in a case nobody thought about. When something reaches the wrong people, read how who gets it is decided, and look for a default.

Case 4: "Every deploy fails its healthcheck"

Commits: 9865d5e and 222326a · Where: Railway deploys

Symptom: The app built fine, but Railway marked every deploy as failed. It never went live.

What was wrong, part 1 (222326a): Railway checks /api/health/ with the header Host: healthcheck.railway.app. Django only answers hosts listed in ALLOWED_HOSTS; anything else gets 400 DisallowedHost. The healthcheck host wasn't listed.

Part 2 (9865d5e): Production redirects HTTP to HTTPS, except for paths in SECURE_REDIRECT_EXEMPT. The patterns were r'^/api/' and r'^/$'. But Django matches them against the path without the leading slash (api/health/), so ^/api/ never matched. The healthcheck (plain HTTP, internal) got a 301 to HTTPS and counted it as a failure.

# SecurityMiddleware matches these against request.path with the leading slash
# stripped, so patterns must not start with one — '^/api/' silently never matches.
SECURE_REDIRECT_EXEMPT = [r'^api/', r'^$']

The pattern: Settings that "silently never match" are the worst bugs: no error, just nothing happening. When a setting seems ignored, check the exact format the framework expects in the docs. Also: prod.py code only runs in production. Locally you'd never see this.

Case 5: "pip can't install the requirements"

Commit: e7855a9 · Where: deploy build

Symptom: The build failed with InvalidRequirement on the first line of requirements.txt. The line looked perfectly normal.

What was wrong: The file had been saved with a UTF-8 BOM: an invisible marker some Windows editors put at the very start of a file. pip read it as part of the first package name.

The fix: re-save the file as plain UTF-8 (no BOM).

The pattern: "The line looks fine but the error says it's wrong" → invisible characters. BOMs, tabs vs. spaces, Windows line endings (\r\n). In VS Code, the status bar (bottom right) shows the file's encoding. Click it to change. On Windows, PowerShell's Set-Content can add a BOM, so watch out when writing files from scripts.

Case 6: "I fixed the validation but still get the old 400"

Where: local development, more than once

Symptom: Changed a check in views.py, python manage.py check passed, but the API still returned the old error.

What was wrong: Nothing in the code. daphne was still running the old version. It doesn't reload on file changes. Same for the Celery worker with tasks and services.

The pattern: "My fix didn't work" → first prove the new code is running. Add a print("NEW CODE") at the top of the function. Not printed? Restart. This is why Lesson 07 starts with Step 0.

Case 7: "Two specialists editing a form together get 429s"

Commit: part of a35b4f0

Symptom: During collaborative form editing, after a few minutes, every page load failed with 429 Too Many Requests.

What was wrong: DRF's UserRateThrottle limits requests per user per minute. It was 200. Collaborative editing is chatty: section autosaves, peer syncs, live refreshes all count. Two active specialists blew through it.

The fix: raise it to 600/min, overridable with USER_THROTTLE_RATE (see the comment in backend/settings/base.py). Dev has throttling turned off entirely, which is why it only showed up live.

The pattern: "Works for a while, then everything fails" → a limit: rate limits, connection limits, memory, quotas (Gemini has them too). Note dev ≠ production: dev disables throttling.

Case 8: "Too many database connections"

Commit: dec5726 · Where: production, when it was on Supabase

Symptom: Errors like EMAXCONN: the database refusing new connections.

What was wrong: The database sat behind a connection pooler with a limit. Django was keeping connections open (conn_max_age) and each deploy started extra processes. Together they used up every slot.

The fix: in prod.py, conn_max_age defaults to 0 (close after each request), overridable with DB_CONN_MAX_AGE. Also stopped running migrate/collectstatic on every process start.

The pattern: another limit. Also: the comments in prod.py explain why each odd setting is there. Read the comments before "cleaning up" a strange setting. It's probably there because of a bug like this.

2. How a deploy happens

Backend (Railway)

railway.json defines two services built from the same code:

Service Build Start
web (theruni-api) bash build.sh (pip install, migrate, create admin, collectstatic) migrate → provision_admin.py → collectstatic → gunicorn backend.asgi:application -k uvicorn.workers.UvicornWorker …
worker (theruni-worker) bash build.sh celery -A backend worker -l INFO --pool=solo

After starting, Railway hits /api/health/ (HealthView in backend/urls.py). Until it answers 200, the deploy isn't live. That's what Lesson 09 Case 4 broke.

Frontend (Vercel)

Vercel runs npm run build. A TypeScript error fails the build, so the old version stays live. Run npm run build locally before pushing anything big.

3. Which settings file runs?

They all default to dev. setdefault means "use this only if nothing else is set." So production must set the environment variable DJANGO_SETTINGS_MODULE=backend.settings.prod on both Railway services. If the worker were missing it, it would quietly run with dev settings (wrong database, wrong channel layer).

NEXT_PUBLIC_ variables are baked in at build time. Next.js copies their values into the JavaScript when npm run build runs. Change NEXT_PUBLIC_API_URL on Vercel and nothing happens until you redeploy.

Adding a new env var is a deploy step. If your code reads a new variable, someone has to add it on Railway/Vercel before the code goes live, or it'll use the default or crash. Say so in your PR description.

6. Debugging production

You can't add print() and restart. What you can do:

  1. Browser DevTools still work. Network tab, status codes, Response bodies. Same as local. Start here, always.
  2. Railway logs. Each service (web, worker) has its own log stream. 500s print their traceback there (because DEBUG=False hides it from the browser). AI failures show up in the worker logs.
  3. Vercel logs. Build failures (TypeScript errors) and rewrite problems.
  4. Reproduce locally with prod-like settings when you can: same data shape, same role, same steps.
  5. Be careful. Production is real families' data. Don't experiment on it. Never run manage.py shell writes against the live database casually.

Exercises

  1. Trace a live request. A parent opens /dashboard on the live site. List each system the GET /api/students/ request passes through, in order, until it reaches the database.
  2. Why both? Why do WebSockets connect to Railway directly while REST calls go through Vercel? What would break if REST calls went direct too? (Hint: Lesson 09 Case 2.)
  3. Spot the risk. You add REPORTS_BUCKET = os.environ['REPORTS_BUCKET'] to base.py. It works on your laptop because your .env has it. What happens on the next Railway deploy?
  4. Read the table. A feature sends an email. It works locally (you see it in Mailpit) but nobody receives it live. Which row of §4 do you check first?

Answers

  1. Browser → Vercel (next.config.ts rewrite) → Railway web service (gunicorn/uvicorn → Django: backend/urls.py → api/urls.py → StudentViewSet.get_queryset) → PostgreSQL. Then the same path back.
  2. Vercel's rewrite only proxies normal HTTP, not WebSockets. If REST went direct, the cookies would be third-party again, and incognito/Safari logins would break. That's the exact bug Case 2 fixed.
  3. If Railway doesn't have REPORTS_BUCKET set, os.environ['...'] raises KeyError at startup, the healthcheck never passes, and the deploy fails. Use os.environ.get('REPORTS_BUCKET', '') with a sensible default, and add the variable on Railway.
  4. The Email row. Dev sends to Mailpit. Production needs real email settings in its env vars. Then check Railway logs for email errors.

Lesson 11: Plain-English Glossary

Not something to read front to back. It's a dictionary to come back to whenever a word in the code makes your eyes glaze over. Each entry: what it means, and where to see a real one in ARASE.

Sections: ARASE words → Web basics → Frontend → Backend → Background & live → Running & deploying

ARASE words

SPED: Special Education. The whole domain of the app.

IEP (Individualized Education Program): The main document ARASE produces for each student, written with AI from the assessments. Stored as a GeneratedDocument with document_type='IEP'. Generated by api/tasks.py → iep_service.run_iep_generation.

Role: One of ADMIN, TEACHER, SPECIALIST, PARENT. Stored on User.role. Decides almost everything a user can see or do.

Student status: Where a student is in the process: PENDING_ASSESSMENT → ASSESSMENT_SCHEDULED → ASSESSED → ENROLLED ↔ INTEGRATED → ARCHIVED. "Integrated" = in a mainstream classroom with support.

Team / StudentAccess: The staff and parent attached to a student. Each member is one StudentAccess row. No row = can't see the student.

Report cycle: One reporting period for a student (ReportCycle). Forms, trackers, and documents belong to a cycle.

Assessment vs. tracker: Assessments happen once at the start (parent, multidisciplinary /specialist, SPED/teacher). Trackers are filled in every cycle to measure progress.

Section / contribution: The specialist assessment is shared. Each specialist fills their own section, stored as a SectionContribution. Sections can be submitted, reopened, locked, and unlocked.

form_data / translated_data: The JSON column holding a form's answers, and its English translation (filled in by a background job).

Activity event: A record that "something happened" (ActivityEvent), like STUDENT_CREATED or REPORT_READY. Creating one also pushes a live message to the right browsers.

Web basics

Client / server: The client asks (the browser running Next.js). The server answers (Django).

HTTP request / response: One round trip. Request: "GET me student 5's profile." Response: the data plus a status code.

Method (verb): The kind of request. GET read, POST create/do, PATCH/PUT update, DELETE remove. Django view methods match: def get(...), def post(...).

Endpoint / route: An address the backend answers at, like /api/students/5/profile/. Listed in api/urls.py and backend/urls.py.

JSON: The text format data travels in: {"first_name": "Sam", "grade": "3"}.

Status code: The 3-digit verdict. 200 OK, 201 Created, 202 Accepted (queued), 400 Bad Request, 401 not logged in, 403 not allowed, 404 not found, 429 too many requests, 500 crashed, 503 unavailable. (Lesson 07 has the full table.)

Header: Extra info on a request/response: content type, cookies, X-CSRFToken.

Payload / body: The data sent with a request, like { email, password }.

Cookie: A small value the browser stores and sends back automatically to the site that set it. ARASE keeps login tokens in cookies.

First-party vs. third-party cookie: First-party = set by the site you're on. Third-party = set by a different site. Incognito and Safari block third-party cookies. That broke login once (Lesson 09, Case 2).

SameSite: A cookie setting that controls whether it's sent on cross-site requests. Lax locally, None (+ Secure) in production.

CORS: The browser rule that a page from site A can only read responses from site B if B says it's allowed. Configured with CORS_ALLOWED_ORIGINS in the settings.

Redirect (301/302): The server saying "go to this other URL instead." A loop of these is a classic rewrite bug.

Trailing slash: The / at the end of /api/students/. ARASE's URLs all have one. Django's APPEND_SLASH redirects URLs missing it, which caused Lesson 09 Case 1.

CRUD: Create, Read, Update, Delete: the four basic data operations.

Frontend

Next.js: The React framework the frontend is built on.

App Router: Next.js's rule that folders under src/app/ are URLs and page.tsx is the screen. [id] captures part of the URL.

React: The library for building screens out of components. Core idea: describe what the screen looks like for the current data; React updates it when the data changes.

Component: A function that returns a piece of screen (JSX). Always functional components here (team rule).

JSX: The HTML-looking code in a component's return (...). {value} inserts a value; cond && <Thing/> shows <Thing/> only when cond is true.

Props: Inputs passed to a component, like function arguments: <Badge color="red" />.

State: A component's changeable data, made with useState. Changing it redraws the screen.

Hook: A function starting with use… that gives a component a capability: useState, useEffect, useParams, useAuth, useRealtimeRefresh. Custom ones live in hooks/.

useEffect: "Run this after the screen draws, and again when these values change." Where pages fetch data.

useCallback / useMemo: Keep a function or value from being recreated on every redraw. You can mostly read past them. Focus on what's inside.

useRef: A box that holds a value without causing a redraw when it changes. Used for things like the open WebSocket in RealtimeProvider.

Context / Provider: React's way to share one value with the whole app. <AuthProvider> supplies it; useAuth() reads it.

"use client": First line of a file that runs in the browser. Needed for state, effects, and clicks.

Query string / search params: The ?a=1&b=2 part of a URL. Read with useSearchParams(). The workspace uses these heavily to pick what to show.

TypeScript / type / interface: JavaScript plus descriptions of data shapes (email: string). They catch mistakes before running. ProfileData at the top of the student page is free documentation of what the backend sends.

Axios: The library for calling the backend. Configured once in lib/api.ts as api. Team rule: never raw fetch for the backend.

Interceptor: Axios code that runs on every request or response. Ours add the CSRF header and handle 401s.

Rewrite (proxy): A Next.js rule (next.config.ts) that quietly forwards /api/* from the Vercel site to Railway. The browser thinks it's talking to one site.

Sonner / toast: The pop-up messages. toast.success(...), toast.error(...).

Tailwind: Styling with class names like flex gap-2 text-muted. Colors come from tokens defined in globals.css and mapped in tailwind.config.js.

Lint (ESLint): A tool that reads your code and flags likely mistakes. npm run lint.

Build: Turning the source into what actually runs (npm run build). Catches TypeScript errors. If it fails on Vercel, the deploy fails.

Backend

Django: The Python web framework the backend is built on.

Django REST Framework (DRF): The add-on for JSON APIs: APIView, ViewSet, serializers, permissions, throttling.

View: The code that handles one endpoint. APIView (you write get/post) or ViewSet (a whole resource).

ViewSet / ModelViewSet: A view for list/create/retrieve/update/delete at once. StudentViewSet. Wired up by a router.

Router: Makes a family of URLs from one line: router.register(r'students', StudentViewSet).

get_queryset: The ViewSet method that decides which rows this user may see. Most "can't see it" bugs end here.

Base class / inheritance: class AssessmentSectionWriteView(SectionWriteView) means "everything SectionWriteView does, plus changes." If a view looks empty, read its parent.

Serializer: Translates between database rows and JSON. fields = [...] decides exactly what the frontend sees.

SerializerMethodField: A computed field. Its value comes from a get_<name> method.

read_only_fields: Fields the frontend can see but not change.

Model / field: A model is a table (Student); fields are columns (CharField, DateField, JSONField, ForeignKey…).

ForeignKey / related_name: A link to a row in another table, and the name for going backwards. related_name='assigned_users' lets you write student.assigned_users.

__ (double underscore) in queries: "Follow this relationship" or "use this operator." assigned_users__user=me, status__in=[...], email__iexact=....

ORM / QuerySet / .objects: Python instead of SQL. Student.objects.filter(...). Any .objects line touches the database.

N+1 queries: Loading a list (1 query), then running another query for each item (N queries). SerializerMethodFields can cause it. Shows up as slow list pages.

Migration: A recorded change to the database structure, in api/migrations/. Made with makemigrations, applied with migrate. A new model field does nothing until both run.

Signal: "When X happens, also do Y." post_save.connect(trigger_translation_task, ...) at the bottom of models.py queues a translation every time a form is saved.

Middleware: Code that runs on every request before/after the view (security, CORS).

permission_classes: The gate on a view. [IsAuthenticated] = must be logged in. Role checks inside the method add finer rules.

request.user / request.data: The logged-in user (from the cookie) / the JSON body they sent.

Authentication vs. authorization: Who are you? (401 when it fails) vs. are you allowed? (403).

JWT: A signed token proving who you are. Short-lived access token + longer refresh token, both in cookies here.

SimpleJWT: The library that makes and checks those tokens.

HttpOnly cookie: A cookie JavaScript can't read, so scripts can't steal it.

CSRF / CSRF token: Protection against other sites forging requests with your cookies. The frontend sends X-CSRFToken on writes; the backend checks it (enforce_csrf). "403 CSRF Failed" = they didn't match.

Throttle / rate limit: A cap on requests per minute (600/user in production). Over it → 429.

Service: A Python module in api/services/ holding business logic. Views call services.

Management command: A custom python manage.py <name> command, in api/management/commands/ (e.g. reconcile_assessment_workflow).

Django shell: python manage.py shell. A Python prompt with your models loaded, for looking at data directly.

Traceback: The list of calls that led to a crash. Read it bottom-up.

Background & live updates

Celery: A separate program (the worker) that runs slow jobs from a queue. Tasks are in api/tasks.py.

Task: A function marked @shared_task that Celery can run. generate_iep_task, translate_form_data_task.

.delay(...): "Queue this task with these arguments and return immediately." Doesn't run it right there.

Task id / AsyncResult: The ticket number for a queued job, and how the backend asks Celery about it. TaskStatusView → /api/tasks/<id>/status/.

Retry: self.retry(exc=exc) in a task: try again later (up to max_retries).

Polling: The frontend asking "done yet?" on a timer. pollTaskStatus every 3 seconds.

Redis: A fast in-memory store. Here: Celery's job queue, and the channel layer in production.

Broker: The queue Celery reads jobs from. Redis, set by CELERY_BROKER_URL.

Result backend: Where Celery stores finished results. Here the database (django-db), so the web server can read what the worker returned.

WebSocket: A connection that stays open so the server can push messages to the browser. Used for live refresh, the notification bell, and shared form editing.

Django Channels: The library that adds WebSockets to Django.

Consumer: The WebSocket version of a view, in api/consumers.py. (RealtimeConsumer, NotificationConsumer, CollaborationConsumer.)

Channel layer / group: How a message gets from wherever it was created to the right open sockets. Sockets join groups (realtime_admins, realtime_user_7); the server sends to a group. In-memory locally (one program only) unless REDIS_URL is set; Redis in production.

Refresh target: A label like dashboard, student, reports attached to a live message. useRealtimeRefresh({ targets: [...] }) refetches only when one matches.

WS ticket: A 60-second token from /api/auth/ws-ticket/, passed as ?token= when opening a socket, because sockets can't use the proxied cookie.

Running & deploying

Virtualenv (venv/): An isolated Python install with this project's packages.

ASGI / WSGI: How a Python web server runs Django. WSGI = plain HTTP only. ASGI = also WebSockets. ARASE uses ASGI (backend/asgi.py).

daphne: The ASGI server used locally. Doesn't reload on code changes.

gunicorn + uvicorn: The ASGI server setup used in production (railway.json).

Settings (base / dev / prod): Shared config plus per-environment overrides. DJANGO_SETTINGS_MODULE picks one; it defaults to dev.

Environment variable / .env: Settings and secrets kept outside the code. .env locally (never committed), dashboards in production.

NEXT_PUBLIC_: Frontend env vars the browser can see. Baked in at build time: changing one needs a redeploy.

DEBUG: On locally (detailed error pages), off in production (generic errors).

ALLOWED_HOSTS: The domain names Django will answer to. Others get 400.

Healthcheck: A URL (/api/health/) the host pings to decide if a deploy is alive.

Vercel / Railway: Where the frontend / backend run live.

S3 / django-storages: Cloud file storage in production (USE_S3=True). Locally, files go to media/.

Gemini / Ollama / AI_PROVIDER: The AI. Gemini = Google's cloud model. Ollama = a local model. auto = Gemini first, Ollama as backup. Logic in api/services/llm_service.py.

Mailpit / smstrap: Local stand-ins that catch emails / SMS so you can read them without sending anything real.

BOM (byte order mark): An invisible character some Windows tools put at the start of a file. Breaks tools that don't expect it (Lesson 09, Case 5).
